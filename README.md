# Kimi Low-Memory Research

Компоненты для исследования Kimi-K2-Thinking на компьютерах, где веса модели значительно превышают объём RAM. Проект сочетает потоковое чтение весов, ограниченные кэши, последовательное обновление KV и вычисления через MLX на Apple Silicon.

Статус: исследовательская библиотека с reference API и отдельными GPU-компонентами. Готового сервера inference и проверенного полного coding-runtime пока нет. Веса модели в репозиторий не входят.

## Установка и проверки

Из корня репозитория, с Python 3.12 или новее:

```sh
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[reference]'
python -m unittest discover -s tests -v
```

По умолчанию тесты используют небольшие синтетические данные, не скачивают веса и пропускают GPU-проверки. Дополнительные MLX-компоненты устанавливаются на macOS с Apple Silicon:

```sh
python -m pip install -e '.[mlx]'
```

Их импорт выполняется отдельно через `kimi_low_memory.mlx`. Установка MLX не включает GPU-тесты автоматически; для них нужен внешний ограничитель ресурсов и явное включение `KIMI_MLX_TESTS=1`.

CLI поддерживает расчёт KV-бюджета, чтение заголовка одного локального shard и снимок памяти своего процесса:

```sh
kimi-low-memory kv-budget --context 512
kimi-low-memory inspect path/to/model.safetensors
kimi-low-memory memory
```

`inspect` читает заголовок размером до 8 MiB и не загружает веса. `kv-budget` рассчитывает expanded FP32 KV для 61 слоя; результат не включает веса и временные массивы. `memory` использует Mach API и работает только на macOS. Команды запуска полного inference в CLI нет.

## Результаты

На Apple M4 Pro с 24 GiB общей памяти исследовательский прототип показал:

| Проверка | Результат | Что сравнивалось |
|---|---|---|
| Первые пять одинаковых decode-позиций | 65,07 → 30,50 с/токен, 2,13× | Медианы CPU/GPU, включая checkpoint I/O |
| Время до первого токена | Примерно 516 → 128,7 с, около 4× | Исторические CPU/GPU-запуски |
| Один полный шаг через 61 слой | 28,73 → 21,32 с, 1,347× | Deferred Q4 с CPU dense против GPU BF16 dense |

Использовался один запрос `Write Python function add(a,b).` и FP32-вычисления с Q4/BF16-весами. GPU сгенерировал 40 токенов, но остановился внутри рассуждения по лимиту длины. Законченного решения задачи и официального BF16-эталона нет. Внешняя нагрузка и файловый кэш не были полностью изолированы; коэффициенты разных опытов нельзя перемножать. [Методика и числа](benchmarks/README.md).

## Компоненты

- Потоковый safetensors reader и reference-вычисления Kimi.
- Ограниченные кэши, prefetch и планирование диапазонов чтения.
- KV-store с проверкой форм, позиции, бюджета и последовательности обновлений.
- Телеметрия памяти процесса и отдельные MLX adapters для Q4/BF16.
- Экспериментальный fused BF16 GEMV без промежуточной FP32-матрицы весов.

Планировщик диапазонов прошёл синтетическую проверку: 24 чтения объединены в 4 при увеличении запрошенного объёма на 1,302%, данные восстановлены побайтно. Fused BF16 GEMV проверен на малых матрицах; ускорение полного Kimi-прогона ещё не измерено. [Исследования](docs/research.md), [архитектура](docs/architecture.md).

Memory budgets относятся к конкретным массивам и буферам, а не ко всей памяти процесса. MLX memory limit имеет рекомендательную семантику. Реальные опыты требуют внешнего watchdog и контроля общей нагрузки машины.
